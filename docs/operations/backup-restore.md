# 备份、恢复与升级

## 备份一致性

数据库保存的是模型、数据集和产物文件的引用，单独备份 PostgreSQL 或单独复制文件都不能形成完整恢复点。

推荐流程：

1. 暂停新导入、训练与清理任务。
2. 等待进行中的原子文件移动结束，记录队列与运行任务快照。
3. 使用 `pg_dump --format=custom` 导出数据库。
4. 对 `/srv/openllmops` 建立文件系统快照，或使用支持校验和与硬链接增量的备份工具；排除可重建的 `model-staging` 与 `upload-tmp` 临时区。
5. 保存当前 `.env` 中非密配置、Compose 文件、镜像 digest 清单和 TLS 证书；密钥进入独立密码库。
6. 计算数据库备份与文件清单的 SHA-256，并把二者标记为同一个恢复点 ID。

模型仓库可能很大。可以使用“数据库每日 + 新增不可变模型/数据集增量”的策略，但仍需定期执行完整恢复演练。

## 恢复顺序

1. 在隔离主机安装同版本 Docker、驱动和 NVIDIA Container Toolkit。
2. 恢复文件快照到新的受控根目录，保持相对路径不变。
3. 启动空 PostgreSQL，导入数据库备份并运行只读一致性检查。
4. 运行对应版本 Alembic 升级；不能先启动会写业务数据的 API。
5. 启动 Node Agent 和监控，盘点 GPU 与残留容器；新主机通常不应存在动态容器。
6. 启动 API/Web，核对模型与数据集清单 SHA-256。
7. 推理服务按期望状态恢复；无法与原容器对账的训练任务标记为 failed，由管理员使用原模型、数据集和配置创建全新任务。首版不支持从 checkpoint 恢复训练。

## 升级与回滚

- 升级前固定新旧镜像 digest，阅读数据库迁移的 upgrade/downgrade，并先备份。
- 数据库迁移与新 API 镜像作为一个发布单元。前端可以提前兼容新旧字段，但不能依赖尚未迁移的列。
- 先在 2 卡环境执行自动化测试与真实 GPU 冒烟，再进入 4 卡主机维护窗口。
- 如果迁移不可逆，回滚方案是恢复整个一致性恢复点，而不是手工删除列。
- 不允许在生产直接编辑已运行容器；所有版本变化写回 Compose/环境配置和 Git。
