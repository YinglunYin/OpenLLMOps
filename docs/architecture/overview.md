# OpenLLMOps 总体架构

## 1. 设计目标

OpenLLMOps 面向一台无 NVLink 的多卡 NVIDIA 服务器。控制面长期运行，推理、训练和测评作为按需工作负载运行。系统首先保证 GPU 分配可解释、任务状态可恢复、导入数据可追溯，再提供便捷的管理界面。

首版边界如下：

- 生产目标为 Ubuntu 22.04、4 × RTX 4090D、128 GB 内存和 2 TB 磁盘；开发环境允许缩减为 2 卡。
- 单张 GPU 在同一时刻只属于一个工作负载；多卡任务必须一次性获得全部所需卡。
- 调度非抢占。训练任务不会自动停止推理服务，GPU 不足时任务排队并提示管理员手工释放资源。
- 推理使用 vLLM；继续预训练和监督微调使用 LLaMA-Factory；测评由独立评测工作负载执行。
- 外部兼容接口仅提供 `/v1/completions`、`/v1/chat/completions`、`/v1/embeddings`，首版不提供 `/v1/responses`。
- 外部模型仅接收 Safetensors，且全局关闭 `trust_remote_code`。

## 2. 逻辑组件

| 组件 | 职责 |
| --- | --- |
| Web | Vue 3 管理界面、Playground 和流式展示 |
| Gateway | HTTPS 终止、管理 API 转发、OpenAI 兼容路由和 API Key 校验 |
| API | FastAPI 业务接口、参数校验、审计记录和状态查询 |
| Scheduler/Reconciler | 队列排序、GPU 原子租约、期望状态与实际状态协调 |
| PostgreSQL | 业务元数据、状态机、租约、事件与审计日志 |
| Node Agent | 在白名单约束下创建、检查和停止动态容器 |
| Dynamic workloads | vLLM、LLaMA-Factory 和评测容器；仅挂载各自所需目录 |
| Prometheus/DCGM Exporter | 控制面指标、GPU 指标和历史查询 |

控制面由 Docker Compose 固定编排。Node Agent 是唯一可以访问容器运行时的组件；API 容器不得直接挂载 Docker Socket。

## 3. 关键数据流

### 3.1 模型导入

1. 用户选择 Hugging Face、ModelScope 或人工受控目录来源；SFTP 仅是系统外的人工传输手段。
2. 下载或复制先进入同文件系统的暂存目录，记录来源、大小、校验和与进度。
3. 校验器拒绝越界路径、软链接逃逸、缺失配置、非 Safetensors 权重和需要远程代码的模型。
4. 校验通过后原子移动至只读模型仓库，并生成不可变版本记录。
5. 失败任务保留错误摘要和可清理的暂存记录，不生成可部署资产。

SFTP 在首版中表示管理员先人工登录服务器完成拷贝，系统只从受控入口目录发现并导入，不保管 SFTP 密码。

### 3.2 推理部署

生成模型与 Embedding 模型分别部署为 vLLM 服务。部署记录同时保存简化表单配置和经过白名单过滤的高级参数。Gateway 根据部署类型发布对应端点，不能把 Embedding 服务误路由到生成端点。

配置编辑采用“生成新修订并协调”的方式；运行中实例不会被原地篡改。停止只改变期望状态，Reconciler 完成容器操作后再更新实际状态。

### 3.3 训练与评测

训练任务引用不可变的模型版本与数据集版本。继续预训练仅支持 LoRA；SFT 支持 Freeze、LoRA 和 QLoRA。产物分为原始 checkpoint、adapter 与合并模型，首版仅允许合并模型直接部署。

评测同时计算通用数据集与领域数据集的正确率，比较基线模型和训练后模型的百分比、百分点变化以及相对变化。系统只呈现量化结果，不设置自动通过阈值。

## 4. GPU 调度一致性

GPU 租约存储在 PostgreSQL，而非进程内存。Scheduler 在事务中锁定空闲设备并一次性写入全部租约；任意一张卡不足时整次申请失败并保持排队，防止部分占卡死锁。

租约包含工作负载 ID、设备 ID、持有者、心跳时间和过期时间。Reconciler 只在确认容器不存在且租约心跳过期后回收，不能仅因一次监控超时释放仍在运行的 GPU。

无 NVLink 环境下，多卡张量并行仍可使用 PCIe，但界面必须提示其通信开销。默认优先单卡可容纳的量化/小模型，多卡参数由管理员显式选择。

## 5. 恢复策略

- 推理部署保存期望状态 `running/stopped`，控制面重启后自动恢复期望为运行的服务。
- 控制面重启后先与仍存在的训练容器按 generation 对账；容器丢失的任务进入 `failed`，训练不会自动重跑。首版不支持 checkpoint resume，需要管理员以原基础模型、数据集与配置新建任务。
- Node Agent 重启后先盘点带 OpenLLMOps 标签的容器，再与数据库对账，禁止盲目重复创建。
- 当前状态、`state_version` 与 `runtime_generation` 持久化在业务记录中；管理员 HTTP 操作进入审计
  日志。首版不提供追加式状态事件表或由事件重建的操作时间线。

## 6. 存储建议

2 TB 磁盘应划分模型仓库、数据集、产物、暂存和日志配额。导入前同时校验下载声明大小与实际剩余空间，并保留安全余量。模型和数据集版本一旦被任务引用就不可原地覆盖，只能创建新版本。
